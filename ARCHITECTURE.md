# Архитектура Stash

Главный принцип: **пользовательские файлы являются обычными файлами файловой системы, а SQLite содержит только служебные данные.** Содержимое и имена файлов не преобразуются и не записываются в БД.

```text
Nginx / HTTPS
    │
    ▼
FastAPI :8080 ── /api и Web UI
    └──────────── /dav/ → WsgiDAV (WSGI adapter)
                         │
SQLite: users, sessions, webdav_tokens
Filesystem: data/users/{user_id}/files/
```

## Компоненты

- `stash/config.py`: настройки из переменных окружения и `.env`.
- `stash/database/`: модели SQLAlchemy и фабрика SQLite-сессий. Alembic-миграции лежат в `migrations/`.
- `stash/auth/service.py`: Argon2id для паролей, случайные серверные сессии, WebDAV-токены. В SQLite хранятся SHA-256-хеши случайных токенов; сырой WebDAV-токен возвращается только один раз.
- `stash/files/storage.py`: операции с файлами через `user_id`; проверка имён, `..`, закодированных путей и символических ссылок; атомарная публикация загруженного файла без перезаписи существующего имени.
- `stash/api/routes.py`: REST API и cookie-аутентификация. Изменяющие запросы требуют заголовок `X-Stash-CSRF: 1`. Cookie — `HttpOnly`, `Secure`, `SameSite=Lax` в рабочей конфигурации.
- `stash/webdav/server.py`: WsgiDAV с Basic auth только по WebDAV-токену. Domain controller устанавливает `user_id` в WSGI environ; провайдер отображает каждый URL на корень конкретного пользователя. WsgiDAV выполняет DAV-методы и блокировки.
- `stash/templates/`, `stash/static/`: серверная HTML-страница, vanilla JS и CSS; интерфейс адаптируется под мобильный экран.

## Границы безопасности

Каждый файловый запрос, включая WebDAV, получает корень через `Storage.root(user_id)`. Путь пользователя не может содержать абсолютный путь, `.` или `..` даже после URL-декодирования. Символические ссылки в компонентах пути отклоняются; WsgiDAV также работает с `follow_symlinks=False`. Папки разных пользователей не используются как общие маршруты. Каталог данных должен быть доступен на запись только процессу Stash и доверенным инструментам резервного копирования.

SQLite содержит только учётные записи, сессии и токены. После выхода сессия удаляется из БД; после отзыва WebDAV-токен не проходит проверку. У токенов высокий уровень энтропии, поэтому SHA-256 используется для поиска по хешу, тогда как пароли хешируются Argon2id.

## Потоки данных

Большая загрузка поступает через `UploadFile`, который временно хранит данные в spooled-файле, затем копируется блоками по 1 MiB во временный файл в конечном каталоге. `os.link` публикует файл без перезаписи, временный файл удаляется. Скачивание отдаётся `FileResponse`, который читает файл потоково и выставляет HTTP-заголовки. WebDAV использует файловый провайдер WsgiDAV.

`/api/storage` возвращает `used`, `available` и `total` для файловой системы, на которой находится каталог пользователя. Поиск по имени проходит дерево файлов без индекса. Это простой вариант для домашнего хранилища на 1–5 человек.

## Развитие

Квоты и шаринг можно добавить поверх `user_id` без переноса файлов. Корзину можно добавить как альтернативную политику удаления в `Storage`. Для согласованных резервных копий нужны файлы и SQLite вместе; миграции БД выполняются перед запуском новой версии приложения.
